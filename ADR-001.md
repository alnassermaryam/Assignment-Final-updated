# ADR-001 - Provider boundary, model aliases, retries, tools, and evaluation
Date: 2026-09-15

## Decision
- All model access sits behind the `ProviderBoundary` ABC; business logic never imports raw SDKs.
- Model IDs resolve from `config.yaml` aliases, never from business-logic string literals.
- Commercial primary, commercial fallback, and OpenAI-compatible open-weight targets are separately configured.
- Retry uses exponential backoff with jitter at the provider boundary. Only idempotent generation is retried automatically.
- Side-effecting tools require explicit authorization and are never silently replayed.
- Pydantic is the application output contract; provider-native JSON Schema is requested where supported.
- Prompts are versioned files. The stable system prefix is kept separate from the volatile user tail.
- Evaluation is a versioned golden set with deterministic checks first, then one-dimension-at-a-time LLM judge rubrics.

## Fallback policy
A production deployment may fall back from `commercial_primary` to `commercial_fallback` only after retry exhaustion and only for idempotent generation. Tool side effects are not retried/fallen back without an idempotency key and an explicit policy.

## Cache policy
Prompt-cache usage is read from provider usage metadata and never assumed. Response-cache keys include prompt version, model ID, normalized input, authorization scope, and tool-state version.
